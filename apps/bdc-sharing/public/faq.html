FAQ

Everything that's worth knowing before you stare at a stuck publish job. Click any question to expand.

How does a publish work, and who runs which step?

The app uses two identities.

  • You (OBO token). Every Unity Catalog read (information_schema, SHOW ALL IN SHARE, DESCRIBE SHARE), the warehouse list, and the privilege changes on the share: GRANT SELECT ON SHARE on publish and REVOKE SELECT ON SHARE on unpublish. Unity Catalog checks your privileges.
  • App service principal. Starts the warehouse, submits and polls the serverless job that calls the BDC Connect SDK, writes the activity log, and runs the pre-flight probes. It doesn't need workspace admin.

A publish is: pre-flight checks, GRANT SELECT ON SHARE … TO RECIPIENT as you, then a one-time job as the SP that runs create_or_update_share, generates the CSN schema (adding the keys you picked), uploads it, and calls publish_data_product.

system.access.audit shows the GRANT/REVOKE under your name and the SDK calls under the SP. The Activity page ties both together.

How do I know the app is set up correctly?

Open Setup. It runs the checks on the warehouse you selected and shows a fix for each open item (a button, or SQL to copy). Required: activity table configured, app SP can read and write it. Recommended: table columns up to date, users can read it. Optional: SAP read KPIs, AI/BI dashboard.

Which install path should I pick: Marketplace or Asset Bundle?

Pick Marketplace (Option A in the README) unless you need to change the source. It installs the app with the sql user-authorization scope. No bundle deploy and no app.yaml edits.

Pick the Asset Bundle (Option B) if you want to fork the app, pin BDC_ACTIVITY_TABLE, or change routes. Both paths run the same code.

Why don't I see any BDC connections?

A BDC connection is a Delta Sharing recipient that SAP BDC creates when the Databricks workspace is connected to BDC. The app lists recipients whose name matches the BDC pattern (by default anything containing "bdc" and "connect", for example bdc-connect-<id>).

If none show up: the connection isn't set up yet in the BDC cockpit, or you can't see the recipient. Ask its owner for USE RECIPIENT. If your recipients use another naming scheme, an admin can set BDC_RECIPIENT_PATTERN (a regular expression) in app.yaml.

What do the pre-flight checks do?

They run automatically when you pick a share and a connection. A red item blocks the publish; a yellow one means the app couldn't prove it and Unity Catalog or the job has the final word.

  • Object types. Only tables are published. Views are blocked by default (see below).
  • Primary keys. Tables without a UC primary key need key columns picked in the panel.
  • You can grant. Whether you own the share (directly or through a group).
  • App can read source tables. If the SP can't, the app grants it USE CATALOG, USE SCHEMA and SELECT as you. If that fails, you get the SQL to hand to a catalog owner.
  • Secret scope. For TOKEN connections, whether the SDK secret scope exists and the SP can read it.
Why does the app grant access to its service principal?

The BDC publish job runs as the app SP. To build the CSN schema and serve the share, it needs USE CATALOG on each catalog, USE SCHEMA on each schema and SELECT on each table the share pulls from.

Pre-flight checks this with one zero-row query as the SP. If it fails, the app runs the grants as you (you need MANAGE or ownership). They are idempotent. Each run is logged as sp_grant_applied.

The GRANT on the share failed. Which privileges do I need?

To grant a share to a recipient you need either:

  • ownership of the share and USE RECIPIENT on the metastore, or
  • USE RECIPIENT, USE SHARE and SET SHARE PERMISSION.

The app stops before any job starts, so nothing needs cleaning up. Ask the share owner or a metastore admin. See Share data to SAP BDC.

Publish fails with "Secret does not exist with scope: sap-bdc-connect-sdk".

The connection uses authentication_type = TOKEN. For TOKEN recipients the SDK reads the BDC tenant settings from a workspace secret scope named sap-bdc-connect-sdk (keys api_url and tenant). OIDC-federated recipients don't need it. Pre-flight now catches this before the job runs.

Preferred fix: recreate the connection with OIDC federation through the SAP BDC onboarding flow. If you have to keep TOKEN, a workspace admin creates the scope once (values from the BDC team):

databricks secrets create-scope sap-bdc-connect-sdk
databricks secrets put-secret sap-bdc-connect-sdk api_url
databricks secrets put-secret sap-bdc-connect-sdk tenant
databricks secrets put-acl sap-bdc-connect-sdk <app-sp-client-id> READ
Do I need to pick primary keys?

Only for tables without a primary key in Unity Catalog. BDC expects a key per entity. Tables with a UC key are picked up as they are. The columns you pick are marked key and notNull in the CSN schema; the table itself is not changed.

Why are views blocked?

Earlier BDC Connect SDK versions failed partway through on views and materialized views. Newer BDC Connect releases are adding view support. Until you have confirmed it for your landscape and SDK version, the app keeps blocking them, so a publish fails in pre-flight instead of inside the job.

To allow them, an admin sets BDC_ALLOW_VIEWS to true in app.yaml and redeploys.

Why does a share show "In BDC" when I never published it through the app?

"In BDC" means a BDC connection holds SELECT on the share in Unity Catalog. A grant made by hand in DBSQL looks the same. If no data product exists in BDC, use Update in BDC: it runs the SDK steps again and is safe to repeat.

The job succeeded but the data product isn't in BDC yet.

BDC picks up new data products on its own schedule, usually within about 15 minutes. If it still isn't there after 30 minutes, run a metadata extraction for the Databricks connection in the BDC cockpit.

When should I use "Update in BDC"?

After the share's tables changed: new columns, new tables in the share, changed keys. It re-sends the metadata and schema and publishes again without touching the grant. The Dashboard lists shares whose source tables changed after their last publish.

What does Unpublish do?
  1. A job as the SP calls delete_share in BDC. This removes the data product, its metadata and schema.
  2. Only if that succeeds, the app runs REVOKE SELECT ON SHARE as you. Consumers keep access if the BDC side fails.

If you close the tab before step 2, the app records the delete as "revoke pending" and finishes the REVOKE the next time you open it. The Dashboard also offers a Finish button. The Databricks share itself is never dropped.

Can I publish the same share to more than one BDC connection?

Yes. Each connection gets its own grant and its own data product. The shares table lists every connection a share is published to, with Update and Unpublish per connection.

What does the Dashboard show, and where does the data come from?
  • Inventory (always): shares in BDC, tables, tables without a UC key, source changes after the last publish. From system.information_schema as you.
  • Publishing (needs the activity log): success rate, activity over time, failures by reason, last publish. Non-admins see their own events.
  • SAP reads (optional): queries, rows and bytes read by BDC connections, from system.access.audit. See the next question.
Is there an AI/BI dashboard?

Yes. On the Setup page, click Create AI/BI dashboard. The app creates and publishes it with your activity table and the selected warehouse, gives you CAN MANAGE, and can share it with a group. Nothing to download or import. After an app update the same place offers Update dashboard.

It runs with each viewer's own permissions: the Publishing page needs SELECT on the activity table, the SAP reads page needs SELECT on system.access.audit.

How do I turn on SAP read KPIs, and what is the trade-off?

A metastore admin grants the app SP read access on the audit table:

GRANT USE CATALOG ON CATALOG system TO `<app-sp-client-id>`;
GRANT USE SCHEMA ON SCHEMA system.access TO `<app-sp-client-id>`;
GRANT SELECT ON TABLE system.access.audit TO `<app-sp-client-id>`;

Trade-off: the SP can then read the whole audit table. The app only queries Delta Sharing query events for BDC connections the viewer can see, but anyone who controls the app's code controls what it reads. If that is not acceptable, skip the grant, or set BDC_USAGE_FROM_AUDIT=false to hide the card.

Do I have to set up the activity log?

Yes, by default. Publish and Unpublish stay blocked until the Setup page's required checks pass: an activity table is configured, and the app SP can write to it on the selected warehouse. That way every action is recorded. An admin can turn this off with BDC_REQUIRE_ACTIVITY_LOG=false.

Create the table on the Activity page (you need MANAGE on the catalog) or adopt one a catalog admin created. Scripted deploys can set BDC_ACTIVITY_TABLE in app.yaml.

The log also gives you outcomes for jobs whose tab was closed (the app checks unfinished runs every minute) and the publishing KPIs on the Dashboard.

Visibility: the Activity page and Dashboard filter to your own events unless you are in BDC_ACTIVITY_ADMIN_GROUP. That filter is applied by the app. Anyone with SELECT on the table can read every row in DBSQL, so grant it accordingly.

Tables created before v2 lack three columns (bdc_connection, share_object_count, source_last_altered). The table owner adds them with one click on the Setup page.

What permissions does the app SP need?
  • CAN USE on the SQL warehouses people use in the app (for activity log writes and pre-flight probes).
  • USE CATALOG / USE SCHEMA / SELECT on the source tables of each published share. Pre-flight grants these.
  • For the activity log: USE CATALOG, USE SCHEMA, SELECT and MODIFY on the table.
  • Optional: SELECT on system.access.audit for SAP read KPIs.

Not workspace admin, and no privileges on shares or recipients. Those are checked against you.

Troubleshooting: "HTTP 502", slow lists, or a stuck page

A 502 comes from the Databricks Apps proxy when a request takes too long or the app restarts. The app answers every request within 25 seconds and keeps working in the background, so the page waits instead of failing. If you still see an error, use Retry.

  • Open /api/health?deep=true&warehouseId=<id> to check the SP token, the warehouse and the activity log.
  • Open /api/diag to see the exact SQL the app runs, and a comparison of information_schema with SHOW GRANTS for a sample of shares.
  • App logs: databricks apps logs <app-name>.
Where do I report bugs or request features?

Open an issue on the project's GitHub repository. Include the share and connection names, the run id from the Activity page, and the exact error.
